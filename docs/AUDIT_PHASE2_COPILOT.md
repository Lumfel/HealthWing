# HealthWing Phase 2 Read-Only Cross-Audit (Copilot Fusion)

**Repository:** [Lumfel/HealthWing](https://github.com/Lumfel/HealthWing)  
**Audit mode:** Read-only cross-audit (no application code modified)  
**Protocol:** `docs/CROSS_MODEL_AUDIT_PROTOCOL.md` Sections 1-4  
**Auditor:** Copilot Fusion  
**Scope:** Privacy/legal gaps, redundancy/dead code, user-vs-vet logical confusion, and head_vet integration plan.

## Executive Summary

The repository contains the Phase 1 baseline security defects and additional structural gaps that block a clean 3-role model (`owner`, `vet_staff`, `head_vet`). The highest-risk issues are plaintext cookie acceptance in `hw_get_encrypted_cookie()`, unauthenticated/unguarded WebSocket signal handling, receipt-chain race/retention defects, rate-limit path/Retry-After behavior, Turnstile local/hostname validation gaps, missing RA 10173 consent capture/logging, missing RA 9268 PRC-license approval and clinical attribution enforcement, broad IDOR/role-boundary weaknesses in legacy admin and owner flows, and a large standalone `admin` surface that conflicts with the target architecture.

## 4. Integration Plan: Fold Head Vet Super-Admin into `vetindex.php`

### 4.1 Target Information Architecture

| Tab | Visible to | Purpose | Server-side guard |
|---|---|---|---|
| Triage & Cases | `vet_staff`, `head_vet` | Active emergency queue, assigned cases, clinical status updates, chat/call. | `hw_require_role(['vet_staff','head_vet'])`; case assignment/ownership checks for vet_staff. |
| Schedule Oversight | `vet_staff` (assigned/read), `head_vet` (full manage) | Calendar/day view, conflict resolution, reassignment, room assignment. | `hw_require_role(['vet_staff','head_vet'])`; mutating actions require `head_vet` or explicit assignment capability. |
| Pet Charts & Rx | `vet_staff`, `head_vet` | Patient chart, checkups, diagnosis/prescription, receipt issuance. | `hw_require_role(['vet_staff','head_vet'])` + approved PRC license check for clinical writes. |
| Staff Approval & Licenses | `head_vet` only | Approve/reject vet_staff, verify PRC license number/expiry/evidence, assign role. | `hw_require_role(['head_vet'])`. |
| Room Management | `head_vet` only | Create/edit/disable rooms, capacity/type, occupancy override with audit reason. | `hw_require_role(['head_vet'])`. |
| Privacy & Traffic Logs | `head_vet` only | Traffic log, privacy audit log, consent records, receipt access audit, 365-day archive purge status. | `hw_require_role(['head_vet'])`; sensitive log redaction. |

### 4.3 Data/Schema Migration Plan

1. Add unified role fields: `veterinarian.Role` enum (`vet_staff`,`head_vet`) or equivalent normalized role table; migrate existing approved veterinarians to `vet_staff`, designate initial `head_vet`.
2. Add RA 9268 fields: `PRC_License_No`, `License_Expiry_Date`, `License_Verified_At`, `License_Verified_By`, `License_Status`.
3. Add RA 10173 consent/audit tables: `privacy_consents`, `privacy_audit_log` (or extend `traffic_log` carefully).
4. Add receipt accountability fields: `Attending_Vet_ID`, `Attending_Vet_Name`, `Attending_PRC_License_No`, `Status` (`ACTIVE`,`PURGED_1YR`) in `receipt_blocks`; preserve block hash headers.
5. Remove legacy `admin`, `medical`, `vet` tables after data migration and FK updates.
6. Backfill/normalize `chat_messages.Sender_Role` and session role values to `owner`, `vet_staff`, `head_vet`, `system`.

### 4.4 UX/Terminology Guardrails

- Use plain owner-facing labels: "My Appointments", "Emergency Case", "Case Status", "Clinic Receipt", "Verification Status".
- Keep internal/security details in staff-only panels: hash chain, Merkle root, triage score internals, traffic/IP logs.
- Every loading indicator label must be `Loading...`.
- No emojis; no changelog/release-note wording in UI/docs/comments.
- Vet staff must not see Staff Approval, Privacy/Traffic Logs, or destructive room/schedule governance controls.
